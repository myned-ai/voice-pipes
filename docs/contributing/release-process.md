# Release process

**Status:** draft
**Last verified:** 2026-10-04
**Owner:** Maintainers

Versions follow semantic versioning. Every crate in the workspace but the
SDK shares one version, `[workspace.package] version` in the root
`Cargo.toml` (a workspace rule holds new crates to it); until 1.0 a minor
version of those may contain breaking changes, called out in the changelog
with a migration note. `voice-pipes-sdk` has its own version and is
released apart, under its [stability policy](../extending/sdk-stability.md).

## Cutting a release

1. **Make sure `main` is green**: the `core-tests` workflow passed on the
   commit you are releasing. The tag workflows check this themselves
   (`scripts/require-green-ci.sh`): each waits for `core-tests` on the tagged
   commit and stops, publishing nothing, unless a run of it passed.
   Run the quickstart and example readiness suite locally:
   `cargo test -p voice-pipes-cli --test quickstart_and_examples -- --nocapture`
   to ensure no example config syntax or documentation command has drifted.
2. **Bump the version** in the root `Cargo.toml`: `[workspace.package]
   version`, and the matching `version = "…"` on each workspace crate under
   `[workspace.dependencies]` (crates.io resolves them by it); and in
   `voice-pipes-admin/frontend/package.json`. Run `cargo build` so
   `Cargo.lock` follows. The SDK's version changes only in an SDK release
   (below).
3. **Move the changelog.** In `CHANGELOG.md`, rename `## [Unreleased]` to
   `## [X.Y.Z] - YYYY-MM-DD`, add a fresh empty `## [Unreleased]` above it,
   and update the compare links at the bottom.
4. **Commit and tag:**

   ```sh
   git commit -am "Release vX.Y.Z"
   git tag -a vX.Y.Z -m "Voice Pipes X.Y.Z"
   git push origin main vX.Y.Z
   ```

5. **Let the tag workflows run.** Pushing a `v*` tag builds:
   - every crate but the SDK, published to crates.io in dependency order
     (`publish.yml`, trusted publishing; the tag must match the workspace
     version or the job stops before publishing anything);
   - CLI binaries for Linux x86_64, macOS arm64 and Windows x86_64 with
     shell and PowerShell installers (`release.yml`, generated by `cargo dist`);
   - container images `voice-pipes` (worker and orchestrator: one image,
     different command), `voice-pipes-admin-frontend` and
     `voice-pipes-admin-backend` pushed to GHCR tagged with the version and
     `latest` (`images.yml`), each checked to run as a non-root user before
     it is pushed.

   The CUDA and VibeVoice images are not published; they are built from
   source by the launcher because of runner cost.
6. **Publish the GitHub Release.** Paste the changelog section as the release
   notes. Mention runtime dependencies that installers do not bring
   (`espeak-ng` for Piper).

## Releasing the SDK

The SDK is released when its own changes call for it, not with every
workspace release. Bump `version` in `voice-pipes-sdk/Cargo.toml` and the
`voice-pipes-sdk` entry under `[workspace.dependencies]` as its stability
policy says (a minor release only adds; `cargo semver-checks` in CI holds
the version to the change), add its changelog line, merge, then run the
`publish` workflow by hand (Actions, *publish*, *Run workflow*,
`target: sdk`). Release a new SDK before a workspace release that needs it:
the workspace's crates are published against the SDK version on crates.io.

## crates.io: the first time

Trusted publishing needs each crate to exist on crates.io first, so the
first release of each crate is published by hand, once:

1. Log in with an API token scoped to publishing new crates:
   `cargo login`.
2. Publish the SDK, then the rest, in dependency order:
   `cargo publish -p voice-pipes-sdk`, then
   `cargo publish --workspace --exclude voice-pipes-sdk`.
3. For each crate, on crates.io: *Settings*, *Trusted Publishing*, add
   GitHub repository `myned-ai/voice-pipes`, workflow `publish.yml`, environment
   `crates-io`. Create the `crates-io` environment in the repository
   settings (add required reviewers there to gate every publish).
4. Revoke the API token. From here on, releases publish from CI.

Published versions are permanent: crates.io can yank a version (no new
dependents) but never delete it, and a name, once taken, stays taken.

## Changelog discipline

Every user-facing change adds a line under `## [Unreleased]` in the pull
request that makes it, under one of *Added*, *Changed*, *Deprecated*,
*Removed*, *Fixed*, *Security*. Documentation-only, test-only and internal
refactors do not need an entry. A breaking change says what breaks and what
to change in a config or client.

## After the release

- Check that `docker pull ghcr.io/<org>/voice-pipes:X.Y.Z` works anonymously
  (one engine image serves workers and the orchestrator; the admin console is
  `voice-pipes-admin-frontend` and `voice-pipes-admin-backend`). GHCR packages
  default to private on first push; flip them to public once.
- Verify what was published:

  ```sh
  gh attestation verify voice-pipes-cli-x86_64-unknown-linux-gnu.tar.xz --repo <owner>/<repo>
  gh attestation verify oci://ghcr.io/<owner>/voice-pipes:X.Y.Z --repo <owner>/<repo>
  cosign verify ghcr.io/<owner>/voice-pipes:X.Y.Z \
    --certificate-identity-regexp 'https://github.com/<owner>/<repo>/' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com
  ```
- Bump nothing else; development continues against `[Unreleased]`.

## The machinery

- `.github/workflows/release.yml` is **generated** by `dist generate` from
  `dist-workspace.toml` (cargo-dist 0.32), then has every `uses:` pinned to a
  commit SHA by hand (tag in a trailing comment) and, also by hand, the
  green-CI step as the `plan` job's first step with `actions: read`. `allow-dirty = ["ci"]` in
  `dist-workspace.toml` tells `dist` that difference is intended; without it
  the workflow's own `dist plan` refuses to run. To change targets,
  installers, system dependencies or provenance: edit `dist-workspace.toml`,
  remove `allow-dirty` for one `dist generate`, re-pin the actions (a new
  action's SHA from `git ls-remote --tags <repo>`), put `allow-dirty` back,
  and check with `dist plan`. Only `voice-pipes-cli` is marked distributable
  (`[package.metadata.dist] dist = true`); the engine crate's
  `voice-pipes-component` binary is not released.
- Release archives are named `voice-pipes-cli-<target>.tar.xz` / `.zip` and
  contain the `voice-pipes` binary, `CHANGELOG.md`, `LICENSE` and `README.md`,
  with a `sha256.sum` and one-line installers
  (`voice-pipes-cli-installer.sh`, `voice-pipes-cli-installer.ps1`).
- Every release binary is built with `cargo auditable` (its dependency list
  is embedded and can be scanned later with `cargo audit bin`), ships a
  CycloneDX SBOM, and gets a GitHub build-provenance attestation.
- `.github/workflows/images.yml` builds the three container images with
  Docker Buildx and pushes them to GHCR, with BuildKit provenance and an SBOM
  attached, a GitHub build-provenance attestation pushed to the registry, and
  a keyless Sigstore signature.
- `dist plan` locally previews exactly what a tag would publish.
- **Protect the release tags** in the repository settings (Rules,
  Rulesets, a tag ruleset targeting `v*`): restrict creation, update and
  deletion to the maintainers who release, and block force pushes. The
  workflows above trust whoever can push a `v*` tag; this cannot be set from
  the tree.
- `.github/workflows/publish.yml` publishes to crates.io with trusted
  publishing (`rust-lang/crates-io-auth-action` exchanges the job's OIDC
  token for a short-lived crates.io token; no token is stored). CI's
  *packages* job runs `cargo publish --workspace --dry-run` on every change,
  so a crate that does not build from its published files fails before a
  release does. The engine crate ships only what it builds from (its
  `include` list); deploy files, sidecars and fixtures stay in
  the repository.

This page stays "draft" until a tag has run through both workflows end to
end; then the first-release notes get recorded here.
