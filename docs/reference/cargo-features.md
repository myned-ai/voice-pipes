# Cargo features

**Status:** active
**Last verified:** 2026-10-11
**Owner:** Docs

Features of the `voice-pipes` engine crate. The engine has no default
features; the CLI's defaults are the batteries (`batteries` below) plus the
plugin crates its `[package.metadata.voice-pipes] default-plugins` names, and
`--no-default-features` builds exactly the features named. Enable engine
features on the CLI crate with the `voice-pipes/` prefix, for example
`cargo build -p voice-pipes-cli --features voice-pipes/stt-grpc`.

Both tables are generated by `scripts/gen-reference.py`, the first from
`voice-pipes/Cargo.toml` and the second from `voice-pipes-cli/Cargo.toml`;
CI fails if either is stale.

Plugin providers are features of the **CLI crate** alone, since the engine
does not know them; they are in the [CLI table](#cli-feature-list), after
the notes.

## Notes

- **CUDA.** `cuda` needs the CUDA 12 toolkit at build time; `ort-cuda` needs
  an ONNX Runtime CUDA build with CUDA 12 and cuDNN at runtime, and the
  execution provider is selected per run with `VP_ORT_EP=cuda`. Neither
  builds on public CI runners. See [GPU and CUDA](../guides/gpu-and-cuda.md).
- **Runtime dependencies.** `tts-piper` and the `tts-kokoro` plugin need
  `espeak-ng` on `PATH`; `protoc` is vendored for every gRPC feature.
- **CI feature set.** `realtime,text-grpc` on top of the defaults is what
  the lint and test jobs use. Plain `cargo clippy` on default features is
  expected to be clean too.
- **Docker images.** The worker images are built from the `FEATURES` build
  argument in `voice-pipes/deploy/docker/docker-compose.yml`; the wizard's
  tests check that every provider it offers is in that list.
- **Component server.** `component-server` builds the `voice-pipes-component`
  binary that serves a provider over gRPC; see
  [gRPC split mode](../extending/grpc-split-mode.md).

The CLI's own `ort-cuda` forwards to every linked ONNX plugin that has a
CUDA path (`voice-pipes-stt-parakeet?/ort-cuda`,
`voice-pipes-stt-moonshine?/ort-cuda`, `voice-pipes-tts-piper?/ort-cuda`, `voice-pipes-stt-nemotron?/ort-cuda`,
`voice-pipes-stt-nemotron35?/ort-cuda`, `voice-pipes-tts-kokoro?/ort-cuda`),
so `--features ort-cuda,tts-kokoro` runs Kokoro on CUDA when
`VP_ORT_EP=cuda` (or its own `execution_provider = "cuda"`); a CLI test
holds that list complete. The two
turn detectors and Silero (`vad-silero`, a default plugin) are CPU only by
design: each runs a small model once per pause, or once per 32 ms window,
where a GPU round trip would cost more than it saves. The same test holds
them to an explicit CPU-only list, so a new ONNX plugin must either take
`ort-cuda` or be added there.
